Build a self-hosted, ANY.RUN-like interactive malware-analysis platform using **Kubernetes as the orchestration layer and KubeVirt for disposable Windows analysis VMs**.

The goal is to create a research/DFIR sandbox where a user can submit a suspicious file, execute it inside an isolated Windows VM, observe its behavior, collect artifacts, and automatically destroy/revert the environment afterward.

### 1. Architecture

Use these components:

* Kubernetes
* KubeVirt
* Windows 10/11 analysis VMs
* Containerized API/backend
* Kubernetes Job/Controller for analysis lifecycle
* PostgreSQL for metadata
* S3-compatible object storage such as MinIO for samples and artifacts
* Redis or NATS for asynchronous job handling
* WebSocket-based live event streaming
* Optional React/Next.js frontend
* Prometheus/Grafana for infrastructure monitoring

Design the system so that analysis workers are disposable and can run concurrently.

### 2. Analysis lifecycle

Implement this lifecycle:

1. User uploads a sample.
2. Backend stores the sample in object storage.
3. Backend creates an analysis job.
4. Scheduler selects an available analysis worker.
5. Controller creates a fresh KubeVirt Windows VM from a known-clean template/snapshot.
6. Attach the submitted sample to the VM through a controlled mechanism.
7. Start monitoring components inside the VM.
8. Execute the sample.
9. Stream relevant telemetry to the backend.
10. Capture network traffic and filesystem/process artifacts.
11. Stop the VM after a configurable timeout.
12. Collect artifacts.
13. Destroy/revert the VM.
14. Mark the analysis complete.
15. Present the results through the web UI.

Never reuse a potentially contaminated VM as a clean analysis environment.

### 3. Windows analysis VM

Create a Windows VM template containing legitimate defensive/research tooling such as:

* Sysinternals Process Monitor
* Process Explorer
* Autoruns
* Windows Event Logs
* PowerShell logging
* Windows Defender telemetry where appropriate
* Wireshark/tshark or equivalent packet-capture capability
* A custom analysis agent

The agent should communicate with the backend over an authenticated channel and provide events such as:

* Process creation
* Process termination
* Command-line information
* File creation/modification
* Registry modifications
* Network connections
* DNS activity
* Selected Windows event information

Keep the agent modular so additional collectors can be added later.

### 4. Networking

Design a strongly isolated analysis network.

Requirements:

* Analysis VMs must not have access to the Kubernetes control plane.
* Analysis VMs must not be able to reach arbitrary internal services.
* Separate management traffic from simulated Internet/sample traffic.
* Provide a controlled network gateway.
* Capture traffic from analysis VMs.
* Make Internet access configurable per analysis.
* Provide a completely offline mode.
* Prevent accidental access to host infrastructure.

Document the network topology and Kubernetes/KubeVirt networking configuration.

### 5. Security model

Treat every submitted sample as potentially hostile.

Implement:

* Disposable VMs
* Clean VM templates/snapshots
* Strict network segmentation
* Resource limits
* Analysis timeouts
* No shared credentials between analyses
* No access from analysis VMs to Kubernetes credentials
* No host filesystem sharing
* No Kubernetes service-account credentials inside analysis VMs
* Authentication between the VM agent and backend
* Artifact sanitization and controlled storage
* Audit logging

Clearly separate the **management plane**, **analysis plane**, and **artifact storage**.

### 6. Backend

Use a language/framework suitable for Kubernetes integration, preferably Go or Python.

Implement APIs for:

```text
POST   /api/analyses
GET    /api/analyses
GET    /api/analyses/{id}
POST   /api/analyses/{id}/stop
GET    /api/analyses/{id}/events
GET    /api/analyses/{id}/artifacts
```

The backend should expose a WebSocket endpoint for live analysis events.

Create database models for:

* Analysis
* Sample
* VM
* Event
* Artifact
* Network connection
* Process
* User

Do not put large binaries directly into PostgreSQL.

### 7. Kubernetes controller

Create a controller/operator that manages an `Analysis` custom resource.

Example conceptual resource:

```yaml
apiVersion: malwarelab.example.com/v1alpha1
kind: Analysis
metadata:
  name: analysis-123
spec:
  sample:
    objectKey: samples/abc123
  profile:
    vmTemplate: windows-11-base
    timeoutSeconds: 300
    networkMode: isolated-internet
  resources:
    cpu: "4"
    memory: 8Gi
```

The controller should manage the state machine:

```text
Pending
  ↓
Provisioning
  ↓
Ready
  ↓
Running
  ↓
Collecting
  ↓
Cleaning
  ↓
Completed
```

Also handle:

```text
Failed
Cancelled
Timeout
CleanupFailed
```

Cleanup must be idempotent.

### 8. KubeVirt

Use KubeVirt VirtualMachine/VirtualMachineInstance resources.

Create a reusable Windows VM template.

Do not build a VM from scratch for every analysis if a clean template/snapshot can be used.

The implementation should support:

* VM cloning
* Snapshot/revert or disposable VM creation
* CPU/memory configuration
* Persistent or ephemeral disks as appropriate
* VM lifecycle management
* VM readiness detection
* Automatic cleanup

Make the VM template configurable.

### 9. Sample delivery

Design a safe mechanism for delivering a submitted sample to the Windows VM.

Avoid mounting arbitrary host paths into the VM.

The sample should be retrieved by the analysis agent from controlled object storage or delivered through another explicitly isolated mechanism.

Record:

* SHA-256
* SHA-1
* MD5
* Filename
* Size
* MIME type
* Upload timestamp

Use hashes as primary identifiers.

### 10. Artifact collection

Collect artifacts such as:

* PCAP
* Process events
* File events
* Registry events
* Network events
* DNS queries
* Windows event logs
* Screenshots
* Dropped files
* Memory dump, optionally
* Execution logs

Store large artifacts in object storage.

Generate metadata and hashes for collected files.

### 11. Web interface

Do NOT attempt to implement everything at once.

Implement in phases:

**Phase 1 — Infrastructure**

* Kubernetes

* `Analysis` CRD

### 15. Engineering requirements

Produce actual working code rather than pseudocode wherever practical.

For every component:

* Explain its purpose.
* Provide source code.
* Provide configuration.
* Provide Kubernetes manifests/Helm templates.
* Provide tests.
* Provide commands to build and run it.

Use interfaces between components so implementations can be replaced later.

Make all timeouts, VM sizes, storage locations, network modes, and concurrency limits configurable.

Do not hard-code credentials, API keys, cluster names, IP addresses, or secrets.

### 16. Important safety requirement

This is a malware-analysis/research environment. Design it specifically for **isolated defensive analysis**.

Do not design the platform to spread samples, evade security controls outside the sandbox, compromise third-party infrastructure, or persist outside disposable analysis environments.

The primary security objective is:

**A malicious sample must be able to compromise the Windows analysis VM without gaining access to the Kubernetes cluster, host system, credentials, internal network, or other analysis sessions.**

Start by producing:

1. A complete architecture diagram.
2. Technology choices with justification.
3. Repository structure.
4. Phase 1 implementation.
5. Kubernetes + KubeVirt manifests for one disposable Windows analysis VM.
6. Instructions for creating the clean Windows VM template.
7. A minimal `Analysis` CRD and controller skeleton.
8. A local development/deployment guide.

After Phase 1 is working, proceed incrementally to Phase 2 rather than generating the entire platform in one step.
